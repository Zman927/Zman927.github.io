멀티테넌트 인사관리 시스템 백엔드

2026.09 ~ 진행 중, 캡스톤디자인 4인 팀에서 백엔드 담당 (백엔드 2명 중 1명)

전공심화과정 졸업 작품으로 4인 팀이 시작한 프로젝트입니다. 교수님이 주신 요구사항은 ERP 프로그램을 만드는 것이었고, 저희는 여러 회사가 함께 쓰는 인사관리 시스템을 만들었습니다. 저는 백엔드 2명 중 한 명으로 요구사항을 정하고 결과를 검증했고, 제 담당 PR은 47건이 머지됐습니다. 백엔드가 처음이라 코드만 보고는 판단하기 어려워, 앱을 직접 조작하고 시연 녹화를 보며 기능 단위로 확인했고, 녹화에서 직원 등록 화면에 급여 입력이 빠진 것을 찾아 다시 넣었습니다.

화면 3장

직원 대시보드

로컬에서 데모 회사 데이터로 띄운 화면입니다. 화면은 팀원이 만든 프론트엔드이고, 저는 백엔드를 맡았습니다.

한 회사용 설계를 여러 회사가 함께 쓰는 구조로 바꾸기

문제
처음 설계는 한 회사가 설치해서 쓰는 구조여서, 회사마다 다른 휴가 규정과 급여 방식, 조직도를 담을 수 없었습니다.
원인
데이터와 설정이 회사 단위로 나뉘어 있지 않았습니다. 여러 회사의 데이터를 한 DB에 두면 조회 조건에 회사 ID를 한 군데라도 빠뜨렸을 때 다른 회사 데이터가 보이게 됩니다.
해결
처음 가입할 때 회사 정보를 입력하고 각 회사 관리자가 직접 설정하는 구조로 바꿨습니다. 요청마다 로그인 토큰에서 회사를 꺼내 TenantContext에 담고, Hibernate의 @TenantId로 JPA 엔티티 조회에 회사 조건이 자동으로 붙게 했습니다. 권한은 @RequirePermission과 인터셉터로 검사하고, 팀장이 볼 수 있는 범위는 ScopeResolver 한 곳에서 계산합니다.
검증
공통 기반은 MockMvc 통합 테스트 31개로 확인했고, 모든 테이블에 company_id가 있는지 같은 팀 규칙은 CI의 ArchitectureRuleTest가 PR마다 검사합니다.

동시에 들어온 휴가 철회와 승인이 서로를 덮어쓰는 문제

문제
직원이 휴가를 철회하는 순간 팀장이 최종 승인을 누르면, 승인된 휴가가 취소로 덮어써지거나 취소 단계가 두 개 생길 수 있었습니다. 팀원이 기능명세서와 코드를 대조하다 보낸 지적을 코드로 확인해 찾은 문제입니다.
원인
두 요청이 같은 휴가와 승인 단계를 잠금 없이 각자 읽고, 읽은 시점의 상태로 판단해 저장했습니다.
해결
승인 단계와 휴가 행을 항상 같은 순서로 잠근 뒤 최신 상태를 다시 읽어서 판단하게 했습니다. 잠그는 순서를 고정해 서로 기다리다 멈추는 상황도 막았습니다.
검증
철회와 승인이 동시에 들어오는 경우와 취소 요청이 두 번 동시에 들어오는 경우를 동시성 테스트로 만들었고, 한 요청이 실제로 잠금을 기다리는지 PostgreSQL의 pg_stat_activity로 확인했습니다.

취약점 관리 API 서버

2026.08, 개인 프로젝트

백엔드를 처음 배우면서 API를 만드는 데서 끝내지 않고, 컨테이너 배포와 보안 검사까지 한 프로젝트에서 이어서 해 보려고 시작했습니다. 주제는 앞서 한 Trivy 실습과 이어지도록 취약점 관리로 정했습니다. 처음 조회, 등록, 수정 API는 Express로 직접 작성했고, 이후 PostgreSQL 연동, JWT와 bcrypt 인증, Docker 이미지, Kubernetes 배포, CI 보안 검사를 단계적으로 붙였습니다.

CI/CD와 Kubernetes 배포 흐름

CI (GitHub Actions, main에 push할 때)
  1. npm ci
  2. node:test 테스트
  3. Docker 이미지 빌드
  4. Trivy 차단 검사고칠 수 있는 CRITICAL, HIGH면 실패
  5. Trivy 기록 검사미해결 포함 전부 기록
  6. GHCR에 이미지 푸시
Kubernetes (로컬 minikube)
  1. Deployment파드 2개
  2. ServiceNodePort 3000
  3. SecretJWT 비밀키
  4. 호스트 PostgreSQLhost.minikube.internal

자동 배포는 레지스트리(GHCR)까지입니다. 로컬 minikube는 GitHub에서 접근할 수 없어서, 클러스터에는 이미지를 직접 불러와 배포합니다.

화면 2장

npm을 지우기 전. Trivy 게이트 스캔이 빌드를 막았습니다

내 코드에 없는 취약점이 빌드를 막은 문제

문제
CI의 Trivy 차단 검사가 HIGH 취약점으로 빌드를 막았는데, npm audit 결과는 0건이었습니다.
원인
이미지 안에서 해당 패키지 경로를 추적해 보니, 취약한 패키지는 프로젝트 의존성이 아니라 베이스 이미지에 미리 깔린 npm 자체에 들어 있었습니다.
해결
앱은 실행할 때 npm을 쓰지 않아서, 의존성 설치가 끝난 직후 npm과 npx를 이미지에서 지웠습니다.
검증
로컬에서 Trivy로 다시 검사해 0건을 확인했고, 같은 CI 검사를 통과했습니다. 위 화면에서 지우기 전과 후를 볼 수 있습니다.

컨테이너 보안 파이프라인

2026.07, 개인 실습

컨테이너 보안을 직접 해 보고 싶어서 시작한 첫 실습입니다. Python 앱을 Docker 이미지로 만들고 GitHub Actions에서 Trivy로 검사했고, AI 코딩 도구 없이 직접 했습니다. 여기서 쓴 Trivy 같은 CI 스캐너가 이미지에 들어간 파일의 내용까지 검사하는지는 지금 쓰는 논문에서 실험하고 있습니다.

커밋 순서대로 본 CI 결과(아래가 처음). 3번은 취약한 이미지인데도 통과했고, 4번에서 ignore-unfixed를 빼자 빌드가 막혔습니다

검사가 통과해도 안전한지 알 수 없던 문제

문제
아직 고칠 수 없는 취약점 때문에 빌드가 계속 막히지 않도록 ignore-unfixed 옵션을 켰는데, 그러자 검사가 통과해도 정말 안전한지 알 수 없었습니다.
원인
ignore-unfixed는 패치가 나오지 않은 취약점을 결과에서 빼 버려서, CRITICAL이어도 기록 없이 통과됩니다.
검증
일부러 취약한 베이스 이미지로 되돌렸을 때 옵션을 켠 상태에서는 검사가 통과하고(3번), 옵션을 빼자 빌드가 막히는 것(4번)을 CI 기록으로 확인했습니다.
결과
막는 검사와 기록하는 검사를 나눠야 한다는 것을 알게 됐고, 이후 vuln-tracker에서 고칠 수 있는 취약점만 빌드를 막고 나머지는 전부 기록하는 두 단계 검사를 골라 적용했습니다.

취약점 관리 시스템 설계

2026.09, 소프트웨어공학 4인 팀 설계 과제

소프트웨어공학 수업의 4인 팀 설계 과제였고, 평가 기준은 설계가 얼마나 깔끔한가였습니다. 기능을 나열하기보다 취약점 관리라는 도메인의 규칙이 설계에 드러나게 하는 데 집중했습니다.

ERD 핵심 부분(전체 엔티티 26개 중 9개). 스캐너 원본 결과와 관리 대상 취약점을 나누고, 자산은 공통 테이블과 유형별 테이블로 나눴습니다

도메인 규칙을 설계 요구사항으로 정하기

문제
기능 목록만으로는 같은 취약점이 스캔할 때마다 반복해서 탐지되고, 자산 유형마다 필요한 정보가 다르고, 조치 기한이 정책에 따라 바뀐다는 규칙이 설계에 드러나지 않았습니다.
판단
스캐너가 보낸 원본 결과와 관리 대상 취약점을 나눠, 여러 번 탐지돼도 관리 대상은 하나로 유지하게 했습니다. 위험도와 조치 기한 정책은 테이블로 두고, 자산은 공통 테이블과 서버, 네트워크 장비별 테이블로 나누는 상속 구조로 정했습니다. 4명이 나눠 맡을 때 파트 간 인터페이스도 명시하게 했습니다.
결과
이 요구사항으로 ERD(엔티티 26개), 기능명세서(기능 43개), 역할 분담안을 만들었습니다.
