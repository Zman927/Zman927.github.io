멀티테넌트 인사관리 시스템 백엔드

2026.09 ~ 진행 중, 캡스톤디자인 4인 팀에서 백엔드 담당 (백엔드 2명 중 1명)

전공심화과정 졸업 작품으로, 교수님이 주신 요구사항은 ERP 프로그램을 만드는 것이었고 저희는 여러 회사가 함께 쓰는 인사관리 시스템을 만들었습니다. 코드는 Claude Code가 작성했고, 저는 무엇을 만들지 정하고 결과를 확인했습니다. 제 담당 PR은 47건이 머지됐습니다.

한 회사용 설계를 여러 회사가 함께 쓰는 구조로 바꾸기

문제
처음 설계는 한 회사가 설치해서 쓰는 구조였습니다. 그런데 회사마다 휴가 규정과 급여 방식, 조직도가 달라서, 처음 가입할 때 회사 정보를 입력하고 각 회사 관리자가 직접 설정할 수 있어야 한다고 봤습니다. 여러 회사의 데이터가 한 DB에 있으면 조회 조건에 회사 ID를 한 군데라도 빠뜨렸을 때 다른 회사 데이터가 보이게 됩니다.
해결
여러 회사가 함께 쓰는 구조로 바꾸게 했고, Claude Code가 구현했습니다. 요청마다 로그인 토큰에서 회사를 꺼내 TenantContext에 담고, Hibernate의 @TenantId로 JPA 엔티티 조회에 회사 조건이 자동으로 붙습니다. 권한은 @RequirePermission과 인터셉터로 검사하고, 팀장이 볼 수 있는 범위(자기 조직과 하위 조직)는 ScopeResolver 한 곳에서 계산합니다.
결과
이후 만든 API들이 이 공통 기반 위에서 동작하고, 공통 기반은 MockMvc 통합 테스트 31개로 검증했습니다.

영수증 한 장으로 경비를 두 번 청구할 수 있던 문제

문제
다른 사람이 올린 파일이나 이미 진행 중인 청구에 쓰인 영수증도 새 청구에 연결할 수 있었습니다.
해결
팀 노션의 보안 항목 목록에 있던 문제로, Claude Code가 진행할지 물어 승인했습니다. 파일을 연결할 때 서버에서 같은 회사의 요청자가 올린 파일인지, 승인대기나 승인완료 상태인 청구에 이미 쓰였는지를 검사하고, 반려되거나 취소된 청구의 영수증만 다시 쓸 수 있게 했습니다. 프로필 사진과 회사 로고도 같은 규칙을 따릅니다.
결과
재사용을 거부하는 경우를 테스트로 남겼습니다.

동시에 들어온 요청이 서로의 결과를 덮어쓰는 문제

문제
직원이 휴가를 철회하는 순간 팀장이 최종 승인을 누르면, 승인된 휴가가 취소로 덮어써지거나 취소 단계가 두 개 생길 수 있었습니다.
해결
팀원이 기능명세서와 코드를 대조해 보낸 지적이었고, 바로 반영하지 않고 Claude Code에게 코드로 먼저 확인하게 했습니다. 문제가 실제로 있어서, 승인 단계와 휴가 행을 항상 같은 순서로 잠근 뒤 최신 상태를 다시 읽어서 판단하게 고쳤습니다.
결과
철회와 승인이 동시에 들어오는 경우와 취소 요청이 두 번 동시에 들어오는 경우를 테스트로 확인했습니다.

승인함 목록의 N+1 쿼리

문제
승인함과 처리 내역 목록을 열 때 건마다 신청자와 결재 단계를 따로 조회해서, 목록이 N건이면 쿼리가 2N번 더 나갔습니다.
해결
팀원이 지적한 문제였고, Claude Code가 낸 방법 중 페이지에 나온 건들의 ID를 모아 PostgreSQL의 ANY와 unnest로 한 번에 조회하는 안을 골랐습니다.
결과
목록 크기와 상관없이 해당 조회가 페이지당 2번으로 고정됐습니다.
  • 다단계 승인 엔진(승인선, 승인함, 승인자 재지정)과 휴가, 평가, 인사발령, 재직상태 기능 개발
  • 인사발령과 재직상태처럼 과거 이력이 중요한 데이터는 수정이나 삭제 대신 정정 기록을 추가하는 방식으로 처리
  • 급여 계좌번호를 AES-256-GCM으로 암호화해 저장
  • PR마다 스키마와 시드 검증, 전체 테스트, Docker 이미지 빌드를 돌리는 CI를 요청해 붙임

취약점 관리 API 서버

2026.08, 개인 프로젝트

백엔드를 처음 배우면서 API에서 끝내지 않고 배포와 보안 검사까지 이어서 해 보려고 시작했습니다. 처음 조회, 등록, 수정 API는 Express로 직접 작성했고, 이후에는 Claude Code가 한 단계씩 구현하고 설명하면 제가 리뷰하는 방식으로 Docker 이미지, 로컬 쿠버네티스 배포, CI 보안 검사까지 붙였습니다.

내 코드에 없는 취약점이 빌드를 막은 문제

문제
Trivy 검사가 HIGH 취약점으로 빌드를 막았는데 npm audit 결과는 0건이었습니다. 프로젝트 의존성에 없는 패키지가 이미지 안에 들어 있다는 뜻이었습니다.
해결
Claude Code가 이미지 안에서 해당 패키지 경로를 추적해, 베이스 이미지에 미리 깔린 npm 자체가 가진 패키지라는 것을 찾았습니다. 앱은 실행할 때 npm을 쓰지 않아서, 의존성 설치가 끝난 직후 npm과 npx를 이미지에서 지웠습니다.
결과
로컬에서 Trivy로 0건을 확인한 뒤 푸시했고, CI 검사를 통과했습니다.

컨테이너에서 DB 주소가 맞지 않게 되는 문제

문제
코드에 DB 주소가 localhost로 고정돼 있었습니다. 컨테이너 안의 localhost는 호스트가 아니라 컨테이너 자신을 가리키기 때문에, 그대로 컨테이너에 넣으면 DB에 연결되지 않습니다. 컨테이너를 처음 실행하기 전에 Claude Code가 먼저 짚었습니다.
해결
DB 접속 정보를 환경변수로 빼서 Docker에서는 host.docker.internal을, 쿠버네티스에서는 host.minikube.internal을 넣게 했습니다.
결과
코드를 고치지 않고 같은 이미지를 Docker와 쿠버네티스에서 실행했습니다.
  • bcrypt로 비밀번호를 해시해 저장하고 JWT 인증으로 쓰기 요청을 보호, SQL은 모두 parameterized query로 작성
  • JWT 비밀키는 쿠버네티스 Secret으로 분리해 매니페스트를 공개 저장소에 올려도 값이 새지 않게 함
  • node:test 기반 자동화 테스트, GHCR 이미지 자동 푸시

컨테이너 보안 파이프라인

2026.07, 개인 실습 (AI 코딩 도구 없이 직접)

컨테이너 보안을 직접 해 보고 싶어서 시작한 첫 실습입니다. Python 앱을 Docker 이미지로 만들고 GitHub Actions에서 Trivy로 검사했습니다.

ignore-unfixed 옵션이 CRITICAL 취약점을 조용히 통과시키던 문제

문제
아직 고칠 수 없는 취약점 때문에 빌드가 계속 막히지 않도록 ignore-unfixed 옵션을 켰더니, 패치가 나오지 않은 CRITICAL 취약점이 아무 기록 없이 통과됐습니다.
해결
일부러 취약한 베이스 이미지로 되돌려 검사가 빌드를 실제로 막는지 확인하고, ignore-unfixed를 끄고 켜 보면서 이 옵션이 패치 없는 취약점을 기록 없이 통과시킨다는 것을 확인했습니다.
결과
이후 vuln-tracker에서는 고칠 수 있는 취약점만 빌드를 막고 나머지는 전부 기록하는 두 단계 검사로 나눴습니다.
  • Python 앱 이미지에서 나온 취약점 20건(HIGH 18, CRITICAL 2)을 베이스 이미지를 Alpine으로 바꿔 0건으로 줄임

취약점 관리 시스템 설계

2026.09, 소프트웨어공학 4인 팀 설계 과제

도메인 규칙이 설계에 드러나게 요구사항 정리하기

문제
소프트웨어공학 수업에서 취약점 관리 시스템의 설계 산출물을 만드는 팀 과제를 받아 시작했습니다. 평가 기준이 설계가 얼마나 깔끔한가였기 때문에, 기능을 나열하는 것보다 도메인 규칙이 설계에 드러나게 하는 것이 어려운 부분이었습니다.
해결
그 규칙을 요구사항 프롬프트로 먼저 정리했습니다. 스캐너가 보낸 원본 결과와 관리 대상 취약점을 나누고, 위험도와 조치 기한 정책은 테이블로 두고, 자산은 공통 속성과 유형별 속성을 나누는 상속 구조로 하고, 4명이 나눠 맡을 때 파트 간 인터페이스를 명시하라는 내용입니다.
결과
Claude Code가 이 프롬프트로 ERD(엔티티 26개), 기능명세서(기능 43개), 역할 분담안을 작성했습니다.
