개요

전공심화과정 졸업 작품으로 4인 팀이 시작한 프로젝트입니다. ERP라는 넓은 과제를 팀과 함께 인사관리로 좁혔고, 회사마다 휴가 규정과 급여 방식, 조직도가 다르다는 점을 보고 한 회사가 설치해 쓰는 설계를 여러 회사가 가입해 각자 설정하는 구조로 바꾸자고 제가 제안했습니다. 백엔드 2명 중 한 명으로 요구사항을 정하고 결과를 검증했습니다. 코드만 보고 넘기지 않고 앱을 직접 조작하고 시연 녹화를 보며 기능 단위로 확인했고, 녹화에서 직원 등록 화면에 급여 입력이 빠진 것을 찾아 다시 넣었습니다.

화면 3장

직원 대시보드

로컬에서 데모 회사 데이터로 띄운 화면입니다. 화면은 팀원이 만든 프론트엔드이고, 저는 백엔드를 맡았습니다.

문제 해결

01회사 간 데이터 격리와 권한 범위
문제
여러 회사가 한 DB를 함께 쓰기 때문에, 조회 조건에서 회사 ID가 한 군데라도 빠지면 다른 회사의 인사, 급여 데이터가 노출될 수 있었습니다.
원인
회사 조건을 기능마다 직접 붙이는 방식으로는 기능이 늘어날수록 누락을 막기 어렵습니다.
해결
로그인 토큰을 검사하는 JwtAuthFilter가 회사 ID를 TenantContext에 넣고, 모든 엔티티가 상속하는 TenantEntity의 Hibernate @TenantId가 JPA 조회에 회사 조건을 자동으로 붙이게 했습니다. 권한은 @RequirePermission과 PermissionInterceptor로 검사하고, 팀장이 볼 수 있는 범위(자기 조직과 하위 조직)는 ScopeResolver 한 곳에서 계산합니다. JPA를 거치지 않는 JDBC 쿼리에는 company_id 조건을 직접 넣습니다.
검증
JPA 조회가 내 회사 행만 보는지는 TenantIsolationTest로 확인했고, 모든 테이블에 company_id가 있는지와 모든 엔티티가 TenantEntity를 상속하는지는 제가 만든 ArchitectureRuleTest가 PR마다 CI에서 검사합니다. 지금 company를 뺀 테이블 51개가 전부 이 검사를 통과합니다.
02동시에 들어온 휴가 철회와 승인이 서로를 덮어쓰는 문제
문제
직원이 휴가를 철회하는 순간 팀장이 최종 승인을 누르면 승인된 휴가가 취소로 덮어써질 수 있었고, 취소 요청이 동시에 두 번 오면 취소 건이 두 개 생길 수 있었습니다. 팀원이 기능명세서와 코드를 대조하다 보낸 지적을 코드로 확인해 찾았습니다.
원인
두 트랜잭션이 같은 휴가 행을 잠금 없이 각자 읽고, 읽은 시점의 상태로 판단해 저장하는 경쟁 상태였습니다.
해결
철회와 취소를 처리할 때 휴가 행을 PESSIMISTIC_WRITE로 잠그고 최신 상태로 다시 읽어 판단하게 했습니다. 잠그는 순서는 승인 처리와 같게 승인 단계 먼저, 휴가 행 다음으로 맞춰 교착을 막았습니다.
검증
겹칠 수 있는 2가지 경우(철회와 최종 승인, 동시에 두 번 온 취소 요청)를 통합 테스트로 만들었습니다. 최종 승인 트랜잭션을 커밋하지 않고 열어 둔 채 철회 API를 보내, 철회가 잠금을 기다리는 것을 pg_stat_activity로 확인한 뒤 커밋합니다. 철회는 409로 거부되고 휴가는 승인 상태로 남았고, 동시에 두 번 온 취소 요청은 한 건만 생겼습니다.

CI 보안 검사의 파일 콘텐츠 검증 공백 연구 (논문)

2026.08 ~ 진행 중, 개인 연구, 2026.11 디지털산업정보학회 논문지 투고 예정

결과 CI 보안 검사 도구 3종이 폴리글롯 파일 36개 중 2개만 탐지, 위장하지 않은 악성 셸 스크립트에도 결과 없음, 보완 도구의 오탐(이미지당 평균 66.3건)과 처리 시간(Trivy의 32.9배) 측정

개요

Dockerfile의 COPY로 이미지에 들어간 파일의 내용을 CI 단계 보안 검사 도구가 실제로 검사하는지 실험으로 확인하는 연구입니다. 포렌식 실습에서 확장자는 PNG인데 용량이 이상하게 큰 파일을 본 경험에서 출발했습니다. 정상 파일처럼 보이면서 다른 형식을 함께 담은 폴리글롯 파일을 위장 사례로 쓰고, 위장하지 않은 원본을 대조군으로 함께 검사해 위장의 효과와 도구의 검사 범위를 나눠 봤습니다. 도구 버전과 DB 날짜는 모두 고정했습니다.

연구 질문과 데이터

RQ1
CI 보안 검사 도구는 COPY로 들어온 파일을 내용 기준으로 검사해 악성 여부를 판단하는가?
RQ2
그 결과는 위장 여부와 레이아웃(Stack, Parasite)에 따라 달라지는가?
RQ3
콘텐츠 기반 탐지 도구를 더하면 탐지 성능과 오탐, 처리 시간 부담은 어떠한가?
데이터
호스트 6종, 페이로드 3종, 레이아웃 2종을 조합한 폴리글롯 36개와 정상 원본 6개, 대조군 3개. 오탐과 처리 시간은 Docker Hub 공식 이미지 12개의 파일 132,251개로 측정했습니다.
도구
CI 보안 검사 도구 gitleaks, semgrep, Trivy와 콘텐츠 기반 도구 ClamAV, Polydet, file, binwalk, polyfile

주요 결과

01CI 보안 검사 도구는 파일 내용을 판정하지 않았다 (RQ1, RQ2)
측정
파일을 하나씩 두고 gitleaks, semgrep, Trivy로 검사했고, 같은 파일 45개를 alpine 이미지에 COPY해 이미지 단위로도 다시 검사했습니다.
결과
악성 셸 스크립트와 EICAR 테스트 문자열을 담은 폴리글롯 24개는 세 도구 모두 결과가 없었고, 시크릿을 담은 12개는 gitleaks가 ICO 2개만 탐지했습니다. 위장하지 않은 악성 셸 스크립트도 세 도구 모두 결과가 없었습니다.
원인
디버그 로그로 확인해 보니 도구들이 폴리글롯을 확장자나 바이너리 판정으로 검사 대상에서 제외했고, 제외된 파일은 결과에 아무 표시 없이 남았습니다.
의미
이 공백은 위장 때문이 아니라 기존 검사가 파일 내용을 악성 판정 대상으로 삼지 않아서 생긴 것이고, 위장은 원래 판정 대상인 시크릿에서만 탐지를 막았습니다.
02보완 도구를 더할 때 드는 비용 (RQ3)
측정
콘텐츠 기반 도구의 재현율, 공식 이미지 12개에서 나온 오탐, Trivy 대비 처리 시간을 쟀습니다.
결과
재현율은 Polydet이 33.3%로 가장 높았지만 어느 도구도 혼자서 두 레이아웃을 모두 탐지하지 못했습니다. Polydet은 이미지당 평균 66.3건의 오탐이 나왔고, ClamAV는 오탐이 0건이었지만 처리 시간이 Trivy의 32.9배였습니다.
의미
CI 단계에서는 판정 결과만 볼 것이 아니라 실제로 검사된 범위를 함께 확인해야 한다는 점을 정리했습니다.

취약점 관리 API 서버

GitHub 보기

결과 베이스 이미지 안의 npm에서 나온 HIGH 취약점 3건을 0건으로, node:test 테스트 12개, 로컬 Kubernetes에 파드 2개로 배포

개요

Node.js와 Express로 만든 취약점 관리 REST API를 Docker 이미지로 묶어 로컬 Kubernetes(minikube)에 배포하고, GitHub Actions와 Trivy로 CI 단계에서 이미지 보안 검사를 한 개인 프로젝트입니다. API에서 끝내지 않고 배포와 보안 검사까지 한 프로젝트에서 이어 보려고 시작했고, 조회, 등록, 수정 API는 Express로 직접 작성했습니다. 이후 PostgreSQL 연동, JWT와 bcrypt 인증, node:test 테스트 12개, Docker, Kubernetes, CI 보안 검사를 단계적으로 붙였습니다.

화면 2장

npm을 지우기 전. Trivy 게이트 스캔이 빌드를 막았습니다

CI/CD와 Kubernetes 배포 흐름

CI (GitHub Actions, main에 push할 때)
  1. npm ci
  2. node:test 테스트
  3. Docker 이미지 빌드
  4. Trivy 차단 검사고칠 수 있는 CRITICAL, HIGH면 실패
  5. Trivy 기록 검사미해결 포함 전부 기록
  6. GHCR에 이미지 푸시
Kubernetes (로컬 minikube)
  1. Deployment파드 2개
  2. ServiceNodePort 3000
  3. SecretJWT 비밀키, kubectl로 생성
  4. 호스트 PostgreSQLhost.minikube.internal

자동 배포는 레지스트리(GHCR)까지입니다. 로컬 minikube는 GitHub에서 접근할 수 없어서, 클러스터에는 이미지를 직접 불러와 배포합니다.

문제 해결

01내 코드에 없는 취약점이 빌드를 막은 문제
문제
CI의 Trivy 차단 검사가 HIGH 취약점 3건으로 빌드를 막았는데, npm audit 결과는 0건이었습니다.
원인
이미지 안에서 해당 패키지 경로를 추적해 보니, 취약한 패키지는 프로젝트 의존성이 아니라 베이스 이미지에 미리 깔린 npm 자체에 들어 있었습니다.
해결
앱은 실행할 때 npm을 쓰지 않아서, 의존성 설치가 끝난 직후 npm과 npx를 이미지에서 지웠습니다.
검증
로컬에서 Trivy로 다시 검사해 3건이 0건이 된 것을 확인했고, 같은 CI 검사를 통과했습니다. 위 화면에서 지우기 전과 후를 볼 수 있습니다.

GitHub 보기

결과 베이스 이미지를 바꿔 HIGH와 CRITICAL 취약점 20건을 0건으로, 그 20건이 있던 이미지가 ignore-unfixed 옵션 하나로 기록 없이 CI를 통과하는 것을 실험으로 확인

개요

컨테이너 보안을 직접 해 보고 싶어서 시작한 첫 실습입니다. Python 앱을 Docker 이미지로 만들고 GitHub Actions에서 Trivy로 검사했고, AI 코딩 도구 없이 직접 했습니다. 여기서 쓴 Trivy 같은 CI 스캐너가 이미지에 들어간 파일의 내용까지 검사하는지는 지금 쓰는 논문에서 실험하고 있습니다.

커밋 순서대로 본 CI 결과(아래가 처음). 3번은 취약한 이미지인데도 통과했고, 4번에서 ignore-unfixed를 빼자 빌드가 막혔습니다

문제 해결

01ignore-unfixed 옵션이 취약점을 통과시키는 문제
문제
아직 고칠 수 없는 취약점 때문에 빌드가 계속 막히지 않도록 ignore-unfixed 옵션을 켰는데, 그러면 패치가 없는 취약점은 CRITICAL이어도 기록 없이 CI를 통과할 수 있었습니다.
실험
일부러 취약한 베이스 이미지로 되돌린 뒤, 옵션을 켠 상태와 뺀 상태의 CI 결과를 비교했습니다.
결과
로컬 검사에서 HIGH와 CRITICAL 20건이 나왔던 slim 이미지가, 옵션을 켠 상태에서는 아무 기록 없이 검사를 통과했고(3번) 옵션을 빼자 빌드가 막혔습니다(4번). 같은 이미지인데 검사 정책 하나로 결과가 달라졌습니다.
배운 점
스캐너 결과를 그대로 믿기보다 옵션이 무엇을 빼는지 알고 써야 한다는 것을 배웠고, 이후 vuln-tracker에서는 막는 검사와 기록하는 검사를 나눴습니다.
