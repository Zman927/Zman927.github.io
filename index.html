멀티테넌트 인사관리 시스템 백엔드

2026.09 ~ 진행 중, 캡스톤디자인 4인 팀에서 백엔드 담당 (백엔드 2명 중 1명)

Backend, 멀티테넌시, 권한, 동시성

전공심화과정 졸업 작품으로 4인 팀이 시작한 프로젝트입니다. 교수님이 주신 요구사항은 ERP 프로그램을 만드는 것이었고, 저희는 인사관리 시스템을 만들었습니다. 회사마다 휴가 규정과 급여 방식, 조직도가 달라서, 한 회사가 설치해 쓰던 처음 설계를 여러 회사가 가입해 각자 설정하는 구조로 바꾸기로 했습니다. 저는 백엔드 2명 중 한 명으로 요구사항을 정하고 결과를 검증했고, 제 담당 PR은 47건이 머지됐습니다. 백엔드가 처음이라 앱을 직접 조작하고 시연 녹화를 보며 기능 단위로 확인했고, 녹화에서 직원 등록 화면에 급여 입력이 빠진 것을 찾아 다시 넣었습니다.

화면 3장

직원 대시보드

로컬에서 데모 회사 데이터로 띄운 화면입니다. 화면은 팀원이 만든 프론트엔드이고, 저는 백엔드를 맡았습니다.

회사 간 데이터 격리와 권한 범위

문제
여러 회사가 한 DB를 함께 쓰기 때문에, 조회 조건에서 회사 ID가 한 군데라도 빠지면 다른 회사의 인사, 급여 데이터가 노출될 수 있었습니다.
원인
회사 조건을 기능마다 직접 붙이는 방식으로는 기능이 늘어날수록 누락을 막기 어렵습니다.
해결
로그인 토큰을 검사하는 JwtAuthFilter가 회사 ID를 TenantContext에 넣고, 모든 엔티티가 상속하는 TenantEntity의 Hibernate @TenantId가 JPA 조회에 회사 조건을 자동으로 붙이게 했습니다. 권한은 @RequirePermission과 PermissionInterceptor로 검사하고, 팀장이 볼 수 있는 범위(자기 조직과 하위 조직)는 ScopeResolver 한 곳에서 계산합니다. JPA를 거치지 않는 JDBC 쿼리에는 company_id 조건을 직접 넣습니다.
검증
JPA 조회가 내 회사 행만 보는지는 TenantIsolationTest로 확인했고, 모든 테이블에 company_id가 있는지와 모든 엔티티가 TenantEntity를 상속하는지는 ArchitectureRuleTest가 PR마다 CI에서 검사합니다.

동시에 들어온 휴가 철회와 승인이 서로를 덮어쓰는 문제

문제
직원이 휴가를 철회하는 순간 팀장이 최종 승인을 누르면 승인된 휴가가 취소로 덮어써질 수 있었고, 취소 요청이 동시에 두 번 오면 취소 건이 두 개 생길 수 있었습니다. 팀원이 기능명세서와 코드를 대조하다 보낸 지적을 코드로 확인해 찾았습니다.
원인
두 트랜잭션이 같은 휴가 행을 잠금 없이 각자 읽고, 읽은 시점의 상태로 판단해 저장하는 경쟁 상태였습니다.
해결
철회와 취소를 처리할 때 휴가 행을 PESSIMISTIC_WRITE로 잠그고 최신 상태로 다시 읽어 판단하게 했습니다. 잠그는 순서는 승인 처리와 같게 승인 단계 먼저, 휴가 행 다음으로 맞춰 교착을 막았습니다.
검증
최종 승인 트랜잭션을 커밋하지 않고 열어 둔 채 철회 API를 보내, 철회가 잠금을 기다리는 것을 pg_stat_activity로 확인한 뒤 커밋하는 통합 테스트를 만들었습니다. 철회는 409로 거부되고 휴가는 승인 상태로 남았고, 취소 요청이 동시에 두 번 와도 한 건만 생기는 것도 같은 방식으로 확인했습니다.

취약점 관리 API 서버

2026.08, 개인 프로젝트

Backend, Docker, Kubernetes, GitHub Actions, Trivy

Node.js와 Express로 만든 취약점 관리 REST API를 Docker 이미지로 묶어 로컬 Kubernetes(minikube)에 배포하고, GitHub Actions와 Trivy로 CI 단계에서 이미지 보안 검사를 한 개인 프로젝트입니다. 백엔드를 처음 배우면서 API에서 끝내지 않고 배포와 보안 검사까지 이어서 해 보려고 시작했고, 처음 조회, 등록, 수정 API는 Express로 직접 작성했습니다. 이후 PostgreSQL 연동, JWT와 bcrypt 인증, node:test 테스트 12개, Docker, Kubernetes, CI 보안 검사를 단계적으로 붙였습니다.

CI/CD와 Kubernetes 배포 흐름

CI (GitHub Actions, main에 push할 때)
  1. npm ci
  2. node:test 테스트
  3. Docker 이미지 빌드
  4. Trivy 차단 검사고칠 수 있는 CRITICAL, HIGH면 실패
  5. Trivy 기록 검사미해결 포함 전부 기록
  6. GHCR에 이미지 푸시
Kubernetes (로컬 minikube)
  1. Deployment파드 2개
  2. ServiceNodePort 3000
  3. SecretJWT 비밀키, kubectl로 생성
  4. 호스트 PostgreSQLhost.minikube.internal

자동 배포는 레지스트리(GHCR)까지입니다. 로컬 minikube는 GitHub에서 접근할 수 없어서, 클러스터에는 이미지를 직접 불러와 배포합니다.

화면 2장

npm을 지우기 전. Trivy 게이트 스캔이 빌드를 막았습니다

내 코드에 없는 취약점이 빌드를 막은 문제

문제
CI의 Trivy 차단 검사가 HIGH 취약점으로 빌드를 막았는데, npm audit 결과는 0건이었습니다.
원인
이미지 안에서 해당 패키지 경로를 추적해 보니, 취약한 패키지는 프로젝트 의존성이 아니라 베이스 이미지에 미리 깔린 npm 자체에 들어 있었습니다.
해결
앱은 실행할 때 npm을 쓰지 않아서, 의존성 설치가 끝난 직후 npm과 npx를 이미지에서 지웠습니다.
검증
로컬에서 Trivy로 다시 검사해 0건을 확인했고, 같은 CI 검사를 통과했습니다. 위 화면에서 지우기 전과 후를 볼 수 있습니다.

컨테이너 보안 파이프라인

2026.07, 개인 실습

컨테이너 보안, Trivy, CI 검사 정책

컨테이너 보안을 직접 해 보고 싶어서 시작한 첫 실습입니다. Python 앱을 Docker 이미지로 만들고 GitHub Actions에서 Trivy로 검사했고, AI 코딩 도구 없이 직접 했습니다. 여기서 쓴 Trivy 같은 CI 스캐너가 이미지에 들어간 파일의 내용까지 검사하는지는 지금 쓰는 논문에서 실험하고 있습니다.

커밋 순서대로 본 CI 결과(아래가 처음). 3번은 취약한 이미지인데도 통과했고, 4번에서 ignore-unfixed를 빼자 빌드가 막혔습니다

ignore-unfixed 옵션이 취약점을 통과시키는 문제

문제
아직 고칠 수 없는 취약점 때문에 빌드가 계속 막히지 않도록 ignore-unfixed 옵션을 켰는데, 그러면 패치가 없는 취약점은 CRITICAL이어도 기록 없이 CI를 통과할 수 있었습니다.
실험
일부러 취약한 베이스 이미지로 되돌린 뒤, 옵션을 켠 상태와 뺀 상태의 CI 결과를 비교했습니다.
결과
옵션을 켠 상태에서는 검사가 통과했고(3번), 옵션을 빼자 빌드가 막혔습니다(4번). 같은 이미지라도 검사 정책에 따라 결과가 달라졌습니다.
배운 점
스캐너 결과를 그대로 믿기보다 옵션이 무엇을 빼는지 알고 써야 한다는 것을 배웠고, 이후 vuln-tracker에서는 막는 검사와 기록하는 검사를 나눴습니다.

취약점 관리 시스템 설계

2026.09, 소프트웨어공학 4인 팀 설계 과제

요구사항, 도메인 설계, ERD

소프트웨어공학 수업의 4인 팀 설계 과제였고, 평가 기준은 설계가 얼마나 깔끔한가였습니다. 기능을 나열하기보다 취약점 관리라는 도메인의 규칙이 설계에 드러나게 하는 데 집중했습니다.

ERD 핵심 부분(전체 엔티티 26개 중 9개). 스캐너 원본 결과와 관리 대상 취약점을 나누고, 자산은 공통 테이블과 유형별 테이블로 나눴습니다

도메인 규칙을 설계 요구사항으로 정하기

문제
기능 목록만으로는 같은 취약점이 스캔할 때마다 반복해서 탐지되고, 자산 유형마다 필요한 정보가 다르고, 조치 기한이 정책에 따라 바뀐다는 규칙이 설계에 드러나지 않았습니다.
판단
스캐너가 보낸 원본 결과와 관리 대상 취약점을 나눠, 여러 번 탐지돼도 관리 대상은 하나로 유지하게 했습니다. 위험도와 조치 기한 정책은 테이블로 두고, 자산은 공통 테이블과 서버, 네트워크 장비별 테이블로 나누는 상속 구조로 정했습니다. 4명이 나눠 맡을 때 파트 간 인터페이스도 명시하게 했습니다.
결과
이 요구사항으로 ERD(엔티티 26개), 기능명세서(기능 43개), 파트 간 인터페이스 규약을 담은 역할 분담안을 만들었습니다. 산출물 문서 작성에는 Claude Code를 활용했습니다.

웹 해킹 보안 교육 플랫폼

2025.04 ~ 2026.05, 캡스톤디자인 4인 팀에서 프론트엔드 담당

웹 보안 교육, JWT, Vue 3

캡스톤디자인 과제에서 팀이 보안 전공을 살릴 수 있는 주제로 고른 웹 취약점 실습 교육 플랫폼이고, 거의 처음으로 팀 협업을 하며 제대로 개발해 본 프로젝트입니다. 4인 팀에서 프론트엔드를 맡아 Vue 3와 Quasar로 웹 기초 강의에서 취약점 학습 모듈(SQL Injection, XSS, CSRF, Command Injection, File Vulnerability, SSRF), 워게임 문제 11개로 이어지는 학습 화면과 커뮤니티, 관리자 화면을 만들었습니다. 서버를 배포하지 않은 상태여서 팀원 컴퓨터의 백엔드와 제 노트북을 Tailscale로 연결해 테스트했고, 이 프로젝트로 교내 캡스톤디자인 경진대회 본선에 진출했습니다.

화면 4장

웹 취약점 학습 목록

로그인 토큰에서 사용자 정보를 읽는 코드가 계속 맞지 않던 문제

문제
로그인 후 토큰에서 사용자 정보를 꺼내는 코드가 계속 맞지 않았습니다.
원인
jwt-decode 3버전과 4버전은 불러오는 방식과 파일 경로가 다른데, 버전을 오가는 동안 두 방식이 섞여 있었습니다.
해결
4.0.0으로 버전을 고정하고 불러오는 방식을 4버전에 맞춘 뒤, 예전 경로를 쓰던 부분은 빌드 설정에서 새 경로로 연결했습니다.
검증
토큰을 읽는 코드가 한 가지 방식으로 정리됐고, 지금 코드로 빌드가 통과합니다.
